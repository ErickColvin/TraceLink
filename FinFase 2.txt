===============================================================================
1. RESULTADO DE LA FASE
===============================================================================

Se completó el 100 % del alcance frontend definido para la Fase 2.

TraceLink V2 queda como una aplicación frontend profesional y navegable con tres
experiencias completas:

1. Tienda pública CH Market.
2. Portal privado del cliente.
3. Portal operativo para personal y administración.

Todas funcionan actualmente con adapters mock tipados y datos en memoria. No se
implementó backend, base de datos, autenticación remota, pagos, reserva real de
stock ni infraestructura de Fase 3.

La implementación conserva la arquitectura:

Pantalla -> hooks/use cases -> contrato de servicio -> adapter mock actual
                                                 -> adapter HTTP futuro

Las pantallas no importan fixtures ni llaman fetch directamente.

8. PEDIDOS ADMIN
===============================================================================

Rutas: /app/orders y /app/orders/:id.

- Cola responsive con número, cliente, fecha, productos, total, pago,
  fulfillment, estado y acción.
- Búsqueda y filtros por estado, pago, cliente, fulfillment y rango de fechas.

- No se simula un reembolso financiero real.

9. PAQUETES ADMIN Y TRAZABILIDAD
===============================================================================

Rutas: /app/packages, /app/packages/new y /app/packages/:id.

- Cola responsive con tracking, carrier, cliente, contenido, recepción,
  ubicación, estado, días almacenado y acciones.
- Filtros separados por tracking, cliente, carrier, estado y ubicación.
- Recepción con trackingCode, carrier, cliente autorizado, contenido, cantidad,
  cadena de frío, ubicación, peso, fechas y notas.
- El cliente se selecciona desde StaffCustomerService; no se escribe un nombre
  libre para asociar información privada.
- Flujo estándar tipado:
  EXPECTED -> RECEIVED -> STORED -> READY_FOR_PICKUP -> PICKED_UP.
- Excepciones explícitas: INCIDENT, RETURNED y LOST.
- Cada transición crea TrackingEvent con actor, fecha, ubicación y notas.
- Cálculo compartido de tiempo almacenado desde recepción/eventos.
- Detalle con cliente/contacto, carrier, contenido, ubicación, recepción,
  permanencia, notas, timeline y datos de retiro.
- Entrega confirmada con código de retiro y nombre de quien recibe.
- El código solo se verifica y no se almacena.
- Comprobante final de entrega y evento PICKED_UP.

19. LÍMITES MOCK Y DEUDA TÉCNICA CONOCIDA
===============================================================================

Estos puntos son deliberados y deben resolverse con la fuente autoritativa futura:

1. Sesión, carrito y mutaciones están solo en memoria y se reinician al recargar.
2. OrderService cliente y StaffOrderService son instancias separadas; las
   transiciones staff aún no se reflejan en el portal cliente.
3. PackageService cliente y StaffPackageService también son instancias separadas.
4. Cambiar rol/estado de usuario no cambia los permisos de la sesión demo activa.
5. Los reportes usan registros mock estáticos y no agregan mutaciones en vivo.
6. El checkout no reserva, reconcilia ni descuenta inventario.
7. Cambiar minimumStock del producto no migra lotes existentes.
8. Crear un producto no crea un lote de inventario; su stock queda en cero hasta
   que exista aprovisionamiento de inventario.
9. Los movimientos seleccionan lotes existentes y heredan lote/vencimiento; no se
   implementó alta independiente de lotes en esta fase.
10. Dos casts DOM históricos del catálogo permanecen como deuda menor; no se
    introdujeron nuevos casts inseguros.
11. La ruta wildcard /app/* muestra el fallback "Módulo no disponible"; todas las
    rutas nominales de Fase 2 están implementadas.
12. Autorización, propiedad, transiciones, concurrencia e idempotencia deben volver
    a comprobarse en backend.

23. PROPUESTA PARA FASE 3 — NO IMPLEMENTADA
===============================================================================

La Fase 3 debe concentrarse exclusivamente en backend e integración:

1. API versionada y adapters HTTP compatibles con los contratos existentes.
2. PostgreSQL y persistencia de entidades/eventos.
3. Autenticación remota segura, sesión, recuperación y alta real.
4. Autorización, permisos y propiedad de datos validados en servidor.
5. Inventario transaccional, lotes, reservas, concurrencia e idempotencia.
6. Persistencia unificada de pedidos y paquetes para cliente/personal.
7. Integración de pagos solo cuando los contratos de negocio estén definidos.
8. Carga de imágenes, notificaciones, couriers y observabilidad por etapas.
9. Reportes derivados de datos persistidos y exportaciones autoritativas.
10. Pruebas de contrato, integración y E2E contra un entorno backend controlado.

La Fase 3 no debería reconstruir páginas, navegación, formularios, componentes,
workflows visuales, permisos UX ni estados ya terminados en esta Fase 2.
