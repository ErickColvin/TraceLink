1. ESTADO DE LA FASE
======================================================================

La Fase 4 quedó implementada y verificada para ejecución local y pruebas
automatizadas. El flujo completo cubre checkout, reserva de inventario,
orden pendiente de pago, intento de pago, webhook idempotente, aprobación,
preparación, entrega, cancelación, reintento y devolución total.

Estado real estimado: 95 %.

El 5 % pendiente no corresponde a código faltante: es la validación final
contra el sandbox real de Mercado Pago, que requiere credenciales y URLs
públicas provistas por el responsable del proyecto. Mientras no existan esas
credenciales, el proveedor fake permite probar todo el ciclo de forma local.
No se almacenaron ni expusieron secretos en el repositorio.

2. ARQUITECTURA IMPLEMENTADA
======================================================================

- Backend autoritativo para precios, totales, identidad y estados.
- Frontend sin acceso directo a fetch desde componentes; usa servicios HTTP
  o mock seleccionados en la raíz de composición.
- Contratos compartidos con Zod y TypeScript para checkout y pagos.
- Adaptador PaymentProvider para desacoplar el negocio de Mercado Pago.
- Dos proveedores disponibles:
  1. fake, para desarrollo y pruebas deterministas;
  2. mercadopago, mediante la API Orders y consultas autoritativas.
- Persistencia PostgreSQL para pagos, intentos, eventos y devoluciones.
- Importes CLP manejados como enteros.
- Operaciones críticas protegidas con autenticación, permisos, CSRF e
  idempotencia según corresponda.

venta descuenta inventario exactamente una vez al completar la orden.

4. CHECKOUT Y ÓRDENES
======================================================================

Endpoint principal:

POST /api/v1/checkout

Comportamiento:

- Requiere cliente autenticado, CSRF e Idempotency-Key.
- El navegador envía productId y quantity, pero no decide precios ni totales.
- Valida que los productos estén activos y publicados.
- Bloquea y comprueba inventario disponible.
- Crea reservas de inventario.
- Crea una orden PENDING_PAYMENT y snapshots de sus ítems.
- Crea Payment y PaymentAttempt.
- Registra auditoría.
- Solicita al proveedor una URL de pago.
- Devuelve la orden, el intento y checkoutUrl sin confiar en datos del cliente.

Flujo operativo de la orden:

PENDING_PAYMENT --webhook aprobado--> PAID -> PREPARING -> READY -> COMPLETED

PENDING_PAYMENT --cliente--> CANCELLED
PAID --staff con permiso--> REFUNDED

Se eliminó la transición manual PENDING_PAYMENT -> PAID. La aprobación solo
se produce después de consultar y reconciliar el estado con el proveedor.

======================================================================
5. PAGOS, WEBHOOKS, REINTENTOS Y DEVOLUCIONES
======================================================================

Webhook:

POST /api/v1/webhooks/mercadopago

- Verifica la firma cuando se usa Mercado Pago.
- Registra eventos del proveedor y deduplica repeticiones.
- Consulta el estado autoritativo del pago antes de cambiar la orden.
- Tolera eventos duplicados y fuera de orden.
- No degrada un pago desde un estado final a un estado anterior.
- Confirma la reserva cuando el pago queda aprobado.
- Libera la reserva ante estados finales fallidos cuando corresponde.

Acciones adicionales:

- POST /api/v1/me/orders/:id/payment-attempts
  Crea un nuevo intento para la misma orden y vuelve a reservar si hace falta.

- POST /api/v1/me/orders/:id/cancellation
  Permite al propietario cancelar una orden PENDING_PAYMENT, liberando stock.

- POST /api/v1/staff/orders/:id/refunds
  Ejecuta devolución total con motivo, permiso orders.refund, CSRF e
  idempotencia. No repone stock automáticamente porque la devolución de dinero
  no implica por sí sola una devolución física del producto.

El cliente HTTP del proveedor usa timeouts, reintentos acotados, backoff,
Retry-After e idempotencia para operaciones repetibles.

6. FRONTEND IMPLEMENTADO

- Estados de carga, error, vacío, éxito y acciones deshabilitadas considerados.
- Confirmación para acciones destructivas.
- Rutas y servicios mock/HTTP actualizados sin filtrar detalles del adaptador

======================================================================
7. SEGURIDAD Y CONSISTENCIA
======================================================================

- El backend obtiene customerId desde la sesión autenticada.
- Los precios y totales siempre se recalculan en el servidor.
- El frontend no contiene credenciales ni secretos del proveedor.
- La URL de retorno del navegador no se acepta como prueba de pago.
- El webhook no se acepta como verdad sin reconciliación con el proveedor.
- CSRF se aplica a las mutaciones autenticadas del navegador.
- Idempotencia evita órdenes, intentos y devoluciones duplicadas.
- Los eventos del proveedor se deduplican en base de datos.
- El permiso orders.refund limita las devoluciones del portal staff.
- Locks y transacciones reducen sobreventa y carreras de inventario.
- Se corrigió una referencia SQL del checkout que mezclaba UUID y texto.
- Se corrigió el cálculo de fechas del dashboard para evitar desplazamientos
  por conversión de date a timestamptz.
- Se aisló la limpieza de rate limits en pruebas de autenticación para que una
  prueba de 429 no contamine casos posteriores.
