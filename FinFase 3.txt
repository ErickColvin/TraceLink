===============================================================================
1. ESTADO FINAL
===============================================================================

La Fase 3 queda terminada. PostgreSQL es la fuente autoritativa para los
módulos administrativos y del portal cliente cubiertos por esta fase. El
frontend de Fase 2 conserva sus contratos de servicio y ahora puede alternar
entre adapters mock y 14 adapters HTTP reales sin filtrar detalles de
persistencia hacia las pantallas.

El alcance entregado incluye:

- API REST versionada bajo /api/v1 con 51 handlers registrados: 3 de salud y
  48 operaciones funcionales.
- PostgreSQL 18 con contrato Prisma ORM 8, 25 modelos y 7 migraciones
  reproducibles.
- Autenticación real con contraseñas Argon2id, sesiones opacas server-side y
  cookies HttpOnly.
- Protección CSRF, CORS/Origin, Helmet, límites de body, rate limiting
  persistente, request IDs y logs estructurados con redacción recursiva.
- RBAC por organización, seis roles base y catálogo central de 19 permisos.
- Aislamiento multi-tenant y ownership de cliente aplicados en repositorios.
- Persistencia autoritativa de productos, inventario, pedidos, paquetes,
  clientes, usuarios, roles, configuración, dashboard y reportes.
- Seed coherente, idempotente y seguro para desarrollo/test.
- Integración frontend/backend mediante un cliente HTTP central y validación
  Zod en la frontera.
- Pruebas unitarias, contractuales, API, integración PostgreSQL y E2E real con
  navegador.
- Documentación de arquitectura, API, base de datos, seguridad y revisión UI.

No se implementó ningún elemento de Fase 4: no hay pago real, webhook,
integración courier, notificaciones externas, uploads, colas ni microservicios.

2. ARQUITECTURA Y ORGANIZACIÓN
===============================================================================

Monorepo pnpm:

- apps/web: React, TypeScript estricto, Vite, React Router y TanStack Query.
- apps/api: Express 5, TypeScript estricto, PostgreSQL y Prisma ORM 8.
- packages/contracts: DTO, enums, esquemas Zod, permisos y contratos comunes.

El backend mantiene capas separadas:

- rutas/controladores: protocolo HTTP, autenticación, permisos y validación;
- servicios: reglas y orquestación de casos de uso;
- repositorios: SQL y alcance tenant/ownership;
- contratos compartidos: forma estable que consumen los adapters frontend.

Las pantallas no llaman fetch directamente. El composition root selecciona
modo mock o HTTP mediante VITE_DATA_MODE. En ejecución Vitest se fuerza mock
solo cuando MODE=test; un NODE_ENV aislado ya no puede ocultar por accidente
una integración HTTP real.

6. AUTH, RBAC Y SEGURIDAD DE SESIÓN
===============================================================================

Autenticación implementada:

- hash de contraseña Argon2id;
- token de sesión aleatorio, guardado solo como HMAC-SHA-256 en PostgreSQL;
- cookie HttpOnly, SameSite y Secure en producción;
- expiración absoluta e inactividad deslizante;
- revocación individual y revocación de todas las sesiones;
- rotación/bootstrap de CSRF mediante login y /auth/me;
- separación de audiencias customer y staff;
- verificación de usuario, membresía, rol y customer activos en cada sesión.

RBAC:

- el catálogo común contiene 19 permisos;
- se sembraron SUPER_ADMIN, ADMIN, OPERATIONS, INVENTORY, SUPPORT y VIEWER;
- las rutas staff exigen el permiso específico;
- los permisos viajan desde la sesión resuelta por el servidor;
- cambiar rol/estado/membresía invalida las sesiones afectadas;
- se impiden cambios que dejarían la organización sin un SUPER_ADMIN activo.

La autorización del frontend sigue siendo UX. La API es la frontera real.

7. AISLAMIENTO TENANT Y OWNERSHIP DEL CLIENTE
===============================================================================

- El organizationId nunca se acepta desde body o query como autoridad.
- Las rutas públicas resuelven ORGANIZATION_SLUG configurado.
- Las rutas privadas derivan organizationId, actor y audiencia de Session.
- Los repositorios privados requieren organizationId y filtran joins por
  organización.
- Las rutas /me derivan customerId de la sesión; no existe búsqueda libre por
  nombre o correo para obtener pedidos/paquetes propios.
- Un recurso ajeno y uno inexistente producen el mismo 404, evitando enumeración.
- Las pruebas negativas cubren acceso cruzado entre organizaciones y clientes.

15. ENDURECIMIENTO DE SEGURIDAD Y REVISIÓN INDEPENDIENTE
===============================================================================

Se aplicó una investigación previa y una revisión independiente posterior del
parche. Resultado final de los hallazgos confirmados: FIXED.

A. Guard de seed

- Fuente: variables de entorno y placeholders documentados.
- Sink original: hash de credenciales y apertura de PostgreSQL desde seed.ts.
- Invariante: un seed solo puede ejecutarse en development/test, con valores
  reales y validación completa antes de cualquier trabajo sensible.
- Solución: seed-environment.ts, validación Zod sanitizada y pruebas negativas.
- Reproducción original: NODE_ENV inseguro, placeholders y DATABASE_URL de
  ejemplo ya son rechazados antes de la conexión.
- Comportamiento legítimo: seed válido e idempotente sigue funcionando dos veces.

B. Lifecycle de runners

- Fuente: fallos durante migración, seed, Vite, navegador o PostgreSQL embebido.
- Sink original: bloques finally que podían ocultar el error principal.
- Invariante: siempre ejecutar todos los finalizadores y conservar el fallo
  original como causa primaria.
- Solución: runWithCleanup, parada TERM->KILL confirmada, cierre agregado de
  puertos, base y navegador.
- Reproducción original: la limpieza ya no reemplaza ni convierte en verde un
  fallo del flujo principal.
- Comportamiento legítimo: integración y E2E terminan limpiamente en verde.

C. Canonicalización de IP

- Fuente: socket y cabeceras forwarded aceptadas por Express según TRUST_PROXY.
- Sink original: clave de rate limiting de auth y entrega de paquetes.
- Invariante: direcciones equivalentes deben compartir bucket y un forwarded
  inválido no puede crear claves arbitrarias.
- Solución: client-ip.ts con SocketAddress, colapso IPv4-mapped IPv6 y fallback
  seguro a socket/unknown. TRUST_PROXY admite false, saltos enteros o IP/CIDR,
  pero no true global.
- Reproducción original: distintas formas equivalentes de IPv6 ya consumen el
  mismo límite.
- Comportamiento legítimo: proxies expresamente configurados siguen operando.

D. Redacción de logs

- Fuente: objetos, mensajes, errores, headers y URLs, incluso claves codificadas.
- Sink original: serialización de Pino/pino-http.
- Invariante: password, secret, token, session, cookie, authorization, API key,
  pickup code y CSRF nunca deben salir en logs.
- Solución: redacción recursiva, aliases normalizados/decodificados, credenciales
  de URL, query/path y JSON; request serializer explícito y ciclos controlados.
- Reproducción original: /c%73rf/path-secret?c%73rf=query-secret ya redacta
  ambos secretos y conserva únicamente parámetros seguros.
- Comportamiento legítimo: requestId, método, status, ruta segura y campos no
  sensibles continúan disponibles para diagnóstico.

Incertidumbre operativa restante: TRUST_PROXY solo debe habilitarse cuando la
red de despliegue obligue a pasar por ese proxy; los logs de infraestructura
externa también deben tener sus propias políticas de redacción y retención.

21. DEUDA TÉCNICA Y RIESGOS NO BLOQUEANTES
===============================================================================

- El chunk principal del frontend mide 526,41 kB minificado (141,67 kB gzip) y
  supera por poco el umbral informativo de Vite de 500 kB. El build sí pasa; se
  recomienda continuar el code splitting por rutas/proveedores.
- El selector de movimientos trae una ventana de hasta 100 ítems. Debe pasar a
  búsqueda remota paginada antes de catálogos grandes.
- Las ediciones administrativas no críticas siguen estrategia last-write-wins;
  considerar optimistic concurrency si aparecen ediciones simultáneas reales.
- Prisma ORM 8 y embedded-postgres están fijados en versiones RC/beta; cualquier
  actualización debe probar migraciones, generated client y runners.
- test:e2e requiere un navegador compatible instalado o CHROME_PATH.
- La selección de puertos de test tiene una ventana TOCTOU pequeña entre liberar
  la reserva y levantar el servicio; el runner usa puertos dinámicos y cleanup,
  pero un host muy concurrido podría requerir reintentos futuros.
- Producción aún necesita decisiones de infraestructura: TLS extremo a extremo,
  secret manager, restricción real de red del proxy, backups/restore probados,
  métricas/alertas y política externa de retención de logs.
- El canal de provisión del código de retiro, recuperación de cuenta y
  verificación de email pertenecen a trabajo posterior.

Ninguno de estos puntos invalida la finalización funcional de Fase 3.
